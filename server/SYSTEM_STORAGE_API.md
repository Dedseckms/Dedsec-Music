# Статистика и диски

Все маршруты находятся под `/dedsec/profile/v1/admin/`. Нужен Bearer JWT
Navidrome; актуальная роль администратора проверяется сервером при каждом
запросе. Обычному пользователю — `403`. Пароли, аргументы процессов и переменные
окружения не входят в статистику.

## Статистика

`GET system?windowSeconds=3600&points=240` возвращает непосредственно объект:

```json
{"sampledAt":1700000000,"scope":"host","intervalSeconds":5,"cpuCount":4,
 "uptimeSeconds":1000,"processCount":120,
 "latest":{"at":1700000000,"cpuPercent":12.5,"memoryTotalBytes":8000000000,
 "memoryUsedBytes":1500000000,"memoryAvailableBytes":6500000000,"swapUsedBytes":0,
 "load1":0.2,"load5":0.3,"load15":0.4,"rxBytesPerSecond":1000,"txBytesPerSecond":2000},
 "history":[],"processes":[],
 "capabilities":{"hostMetrics":true,"processMetrics":true,"storageCopy":true,"automaticActivation":false}}
```

Все временные метки — числовые Unix seconds. CPU — процент общей доступной
вычислительной мощности; CPU отдельного процесса может превышать 100% при
нескольких ядрах. Первый CPU/network sample может содержать `null`.
До первого sample API возвращает `503 METRICS_WARMING_UP`.

Сбор происходит раз в 5 секунд, независимо от открытого клиента. История хранится
24 часа, ответ ограничен 360 точками и 512 KiB. Параметры: `windowSeconds`
60–86400, `points` 1–360. `latest` и точки истории содержат CPU, память, swap,
load1/5/15 и суммарные RX/TX bytes/s. Накопительные сетевые счётчики интерфейсов
не раскрываются, loopback исключён; на хосте исключены типичные виртуальные
интерфейсы, чтобы уменьшить двойной учёт. Bond/bridge конфигурация может давать
приблизительные агрегаты.

`processes` — до 128 процессов `{id,pid,name,cpuPercent,rssBytes}` с наибольшей
нагрузкой/памятью. `name` — только короткое Linux `comm`. `id` включает время
старта, поэтому повторное использование PID не смешивает графики. `processCount`
считает все видимые PID, чтение деталей ограничено 4096 PID и 0.75 секунды;
`processesTruncated=true` сообщает о неполной выборке. В history не более восьми
записей `{id,cpuPercent,rssBytes}` на точку. Недоступные чужие процессы пропускаются.

В Docker `scope=container`: cgroup CPU/memory относятся к контейнеру, host load
не выдаётся, процессы ограничены PID namespace. Без cgroup counters — `null`,
а не подмена хостовыми значениями. Привилегированный контейнер, host PID namespace
и Docker socket для работы не нужны.

## Копирование на подготовленный диск

`GET storage` → `{volumes:[...],shards:[...],activeJob:null|job}`. Показываются
только настроенные тома и известные логические разделы `tracks`, `yandex`,
`uploads`. `trackCount/indexedBytes` — read-only агрегаты индекса Navidrome,
кешируемые на минуту; `null`, если индекс недоступен. Это не рекурсивный `du`.

По умолчанию дополнительных томов нет и выбрать диск для переноса нельзя.
Оператор сначала определяет физический диск, делает резервные копии и монтирует
его вне приложения. HTTP API никогда не форматирует, не монтирует и не меняет
системные службы. После этого оператор может настроить `STORAGE_VOLUMES`:

```json
[{"id":"extra","label":"Дополнительный диск","root":"/extra","expectedDevice":12345}]
```

`expectedDevice` — проверенный `os.stat('/extra').st_dev` именно смонтированного
целевого файлового раздела; после смены устройства или перенастройки окружения
конфигурацию надо проверить заново. Указанный root должен быть физическим каталогом
вне активной библиотеки, на другом устройстве. Поддерживаются ext4/xfs/btrfs/zfs
с атомарным hardlink no-replace; FAT/NTFS и неизвестные ФС не допускаются. Для Docker
нужен отдельный явный bind этого подготовленного тома в API; существующий Compose
не монтирует дополнительные диски автоматически.

- `POST storage/plans` `{sourceShardId,targetVolumeId}` →
  `{id,planHash,files,bytes,reserveBytes,expiresAt,requiresOperatorActivation:true,warnings}`.
  План живёт 30 минут, фиксирует точные относительные пути, inode/device, size,
  mtime. Ограничение: 100000 файлов, 16 MiB имён, 10 секунд инвентаризации,
  не более 32 сохранённых планов. Симлинки и сторонние hardlink-файлы запрещены.
- `POST storage/moves` `{planId,planHash}` → непосредственно `job`.
- `GET storage/moves/{id}` → `job`.
- `POST storage/moves/{id}/cancel` и `/resume`, тело `{}` → `job`.

```json
{"id":"uuid","state":"running","phase":"copying","filesTotal":100,
 "filesDone":4,"bytesTotal":1000000,"bytesCopied":40000,"errorCode":null,"updatedAt":1700000000}
```

Одновременно выполняется одна задача. SHA256 считается при чтении источника,
затем проверяется чтением копии; публикация на целевом диске атомарная и без
перезаписи. Перед началом и в конце проверяется исходный snapshot. Изменение
библиотеки во время операции останавливает её с `SOURCE_CHANGED`; приложение не
останавливает импорты и загрузки автоматически. Копии находятся только в
`<target>/dedsec-music-copies/<job>/data/<shard>/...`, частичные файлы — в отдельном
приватном staging. Источники всегда читаются и никогда не удаляются.

Скорость по умолчанию 4 MiB/s, блок 256 KiB, поток nice19, чтения разделяют
ограничитель с загрузками/анализом. Проверочные чтения тоже ограничены. Это снижает
конкуренцию с воспроизведением, но не гарантирует latency накопителя. На целевом
диске остаётся резерв 10 GiB. `bytesCopied` учитывает полностью проверенные файлы,
поэтому один большой файл обновляет счётчик после завершения проверки.

Cancel сохраняет приватный partial, resume проверяет его префикс и продолжает без
дублирования; после перезапуска queued/running задачи становятся paused. Конфликт
с чужим файлом, несовпадение SHA, stale plan, пропавший mount или недостаток места
приводят к безопасной остановке. Произвольные пути, команды, монтирование и удаление
через запросы не принимаются.

Успех копирования — **`awaiting_activation`**, а не освобождение места. Для
сохранения ID треков и плейлистов Navidrome должен продолжать видеть прежние
логические пути. Нужен отдельный проверенный операторский bind-mount/cutover-план
и резервная копия перед переключением. Симлинки не подходят при
`FollowSymlinks=false`. Эти шаги и последующее освобождение старого диска API
не выполняет; исходные файлы остаются для отката. Не восстанавливайте старую БД
поверх работающего импорта.

Безопасная предварительная проверка: `python -m unittest discover -s tests`.
Тесты используют только изолированные временные каталоги и маленькие файлы;
проверки копирования в fixture моделируют отдельный том на том же тестовом диске.
